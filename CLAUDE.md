# DADA Portal

B2B ordering portal for DADA Distribución (Spanish food wholesaler; customers are Chinese restaurants). Orders flow to the on-prem Wingest ERP via an outbound-polling bridge.

## Conventions (non-negotiable)
- Money = integer cents everywhere (`unit_price_cents`). Quantities = `numeric(10,3)` / `number` for ALL order lines (fractional exists for weighed products).
- Product/category names = `jsonb {"es": "...", "zh": "..."}`; UI locale zh (default) or es; zh falls back to es.
- Prices are NEVER trusted from the client. `create_order` re-resolves prices server-side from the company's tarifa (tier 1..6 → `price_N_cents`).
- All order writes go through SECURITY DEFINER RPCs. No direct INSERT policies. RLS on every table; catalog requires login.
- DB migrations: SQL files in `supabase/migrations/` (source of truth), applied to cloud project `gudiykhngonoqsjoigza` via Supabase MCP `apply_migration`. Never `db push`.
- SQL constructs are NOT `pg_catalog` functions. `COALESCE`, `LEAST`, `GREATEST`, `NULLIF`, `CASE` are syntax the parser rewrites, so `pg_catalog.coalesce(...)` makes Postgres hunt for a function that does not exist and fail with 42883 — at RUN time, because `create function` validates plpgsql syntax and not name resolution inside its SQL. A migration therefore applies cleanly and the RPC dies on its first real call. Qualify ordinary functions (`pg_catalog.now`, `pg_catalog.array_agg`); never qualify a construct. Cost so far: `staff_bulk_confirm_orders`, 2026-08-22.
- Package manager: pnpm. App gate before commit: `pnpm lint; pnpm typecheck; pnpm test; pnpm build`. With local Supabase running, also run `pnpm db:test`.
- ERP glossary: codart=SKU, codcli=customer no., tarcli=price tier, numped/numalb=ERP doc numbers (bridge writes them back).
- Customer catalog reads go through `products_priced` (one computed price for the caller's tarifa). Authenticated clients can neither read nor insert/update the six `price_N_cents` columns; staff tooling uses the server-only service-role client after `requireStaff`. Ordering gates on `products.is_orderable` (generated: `is_available AND is_current_variant`). Customer code uses the narrow types in `public.types.ts` and never `select('*')` from products.
- Accepted security-advisor baseline: 17 WARNs (authenticated execution of the intentional `create_order`, `staff_confirm_order`, `staff_cancel_order`, `staff_update_order_line`, `staff_provision_customer`, `staff_provision_staff`, `staff_set_customer_active`, `staff_set_staff_active`, `staff_set_staff_role`, `update_own_display_name`, `staff_get_order_bridge_failures`, `staff_requeue_order`, and — added 2026-08-22 — `staff_bulk_confirm_orders`, `staff_reorder_categories`, `staff_update_customer_account`, `staff_update_staff_account`, `staff_update_own_display_name` RPCs) + 1 ERROR (the deliberate definer view `products_priced`) + 1 WARN `auth_leaked_password_protection` (pre-existing Auth project setting, not schema; enabling it is a pending owner decision). Private RLS helpers are outside the exposed API schema. Anything beyond this baseline is a regression.
- User management (create account, change role, activate/deactivate) writes through the service-role client ONLY after `requireStaff` plus the pure role gates in `src/lib/user-admin.ts` — `canManageUsers` (manager+, customer accounts) and `canManageStaff` (owner only, staff accounts). Every action repeats the gate the page used to hide the button; staff self-modification is always rejected (`SELF_FORBIDDEN`), and a half-created account is rolled back with both orphans named in the server log.
- `orders.staff_note` and `companies.notes` are internal and column-revoked from authenticated. Staff transitions write notes only through RPCs; client code enumerates order columns or uses `PublicOrder`. `create_order` uses a UUID `client_token` and rejects content-changing retries. The bridge must claim with `bridge_claim_confirmed`, then pass the same claim token to `bridge_mark_injected`; every bridge mark returns boolean and `false` is an alertable failure.

## Framework note
Next.js 16 has breaking changes vs training data. Before writing framework-level code (routing, middleware/proxy, config), read @AGENTS.md and the relevant guide under node_modules/next/dist/docs/. In Next 16 the middleware file is `src/proxy.ts` (renamed from `middleware.ts`).
